# Development

Use Go 1.27.3. Run `go mod download`, `go build ./...`, `go test ./...`, and `go vet ./...`. Check formatting with `go fmt ./...` (it should print nothing). Run `go test -race ./...` where CGO and a C compiler are available; CI runs it on Linux. Run `go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...` for a vulnerability scan. That scan queries the public Go vulnerability database; the EJECT CLI itself needs no network or AWS account.

Direct runtime dependencies are Cobra v1.10.2 (Apache-2.0) for commands, `gopkg.in/yaml.v3` v3.0.1 (MIT/Apache-2.0) for Compose YAML, and `golang.org/x/sys` v0.49.0 (BSD-3-Clause) for Windows ACL creation and inspection. Modules are locked in `go.sum`.

Unit tests sit beside code. `tests/integration/flow_test.go` exercises inspect → plan → compatibility report → generate → static verify through real CLI commands and compares outputs with reviewed files in `tests/golden/`. The synthetic demo is in `examples/demo/`. Ordinary tests never start containers. After building the demo image and making `postgres:16-alpine` available locally, set `EJECT_RUNTIME_TEST=1` to explicitly opt into the real Docker integration test; it starts an isolated project without pulling images and retains its volume. CI has separate short fuzz and Docker integration jobs; the latter explicitly pulls the PostgreSQL image on the CI runner. Do not regenerate goldens automatically during tests; review each intentional change to rules or public JSON formats.
